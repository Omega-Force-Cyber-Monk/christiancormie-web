### Additional verified staff contract defect (G13)

The guards on GET /vendors/me and GET /vendors/me/qr-code admit VENDOR_STAFF, but VendorsService.getMyVendorProfile calls VendorsRepository.findByUserId(user.sub), which only looks up vendor.userId and has no staff fallback. A normal staff user is associated through vendorStaff.vendorId, so these reads return vendor-profile-not-found. FoodTrucksRepository.findVendorForActor and BookingsRepository.findVendorForActor do implement the active-staff fallback. Treat the vendors/me staff path as a verified backend contract defect, not a frontend missing token or a reason to impersonate an owner. Source: [vendor lookup](../../christinacormie-backend/src/modules/vendors/vendors.repository.ts#L15), [service](../../christinacormie-backend/src/modules/vendors/vendors.service.ts#L59), [staff actor fallback](../../christinacormie-backend/src/modules/bookings/bookings.repository.ts#L27). Backend changes are outside this audit.

## Verified backend behavior requiring frontend care

Registration waits for six-character email verification; pending responses do not establish login. Staff uses email + four-digit PIN, not password login. Vendor platform access and optional verification badge are separate: current services allow APPROVED or PENDING_APPROVAL for platform actions, while suspended/rejected/onboarding states can fail. The old audit's blanket approved/verified wording must not become a frontend gate.

Community lists use limit/offset pagination with nextOffset; social feeds use nextCursor; messaging uses nextOffset; payments transaction lists use page/limit and meta; discovery returns meta.count and foodTrucks, not a global total. Never impose a universal `{data,total}` envelope. Admin management outputs are purpose-built composites; generic detail endpoints may return raw selected models with different nesting.

The gateway exposes conversation:join, conversation:leave, message:send, conversation:read. Realtime service emits message:new and conversation:read. No typing or online-presence contract was found, despite older audit prose mentioning typing. Do not show "online" from fixture booleans as socket presence.

Admin payout reject/hold endpoints are deliberately deprecated and throw 400. Prefer approve/retry when actual actions permit. Backend admin booking dispute presentation derives from review reports (`source: review_reports`), whereas booking issue resolution uses BookingIssue. These must not be treated as identical dispute records.

## Suspected/operational risks (not runtime-confirmed defects)

- Socket connect returns an already connected socket without replacing its auth token; reconnect while connecting can allocate another socket, and unsubscribe closes over the mutable global socket. Currently unused; test and repair when wiring realtime. HTTP refresh does not by itself reconnect the socket.
- Web Locks coordination is conditional on browser support. The fallback is only in-process single-flight; simultaneous refresh rotation across tabs without Locks needs a confirmed supported-browser policy or a tested fallback.
- Existing backend JWT guard verifies signature/expiry without reading current account status on every request. Status mutations/revocation do not necessarily invalidate an already issued access JWT instantly. Confirm revocation expectations with backend owners; frontend guards cannot enforce server authorization.
- Several backend endpoints return selected/raw Prisma records. Read-model expansions may include sensitive fields; DTOs should expose only the reviewed response surface. Staff list explicitly returns PINs to the authorized vendor; do not log or persist them outside the necessary UI.
- Realtime events and mutation responses can duplicate/out-of-order messages. Reconcile by server ID and authoritative refetch; never infer delivered/read solely from a local append.
- Abort/stale responses, rapid filter changes and financial mutation retries need regression scenarios. Payments must follow canonical server status/webhook results, not assume payment-intent creation means payment succeeded.
- Third-party Stripe/Cloudinary/mail/Firebase/RevenueCat configuration and actual CORS origins are unverified. Stripe source contains an environment-controlled mock branch; source implementation does not prove real settlement.
- Leaderboard refresh job scheduling/registration and snapshot freshness need backend operational confirmation; do not advertise live rankings based only on endpoint availability.

## Decisions before implementation

Resolve G01-G03 first. Then fix already-live admin contracts (G04-G09) before widening live usage. Confirm location/timezone, monetary/deposit rules and real entity identity before bookings/payments. Resolve U01/U02/U06/U08/U10/U11/U14/U15/U18 with product/backend owners; frontend adapters cannot manufacture those capabilities.
